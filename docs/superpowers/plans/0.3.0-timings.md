# 0.2.1 group-action timings

Throwaway set: 50 groups of 3 identical JPEGs from `scripts/make-dup-set.mjs`, Files section, similarity 100, burst groups off, dev server on port 4748 with its own data folder. This set is small (about 2 KB per result group), so it shows request counts, not the 2.4 MB reload cost on the real library.

Baseline on `main` was not measured: it needed a second checkout and the set is too small to show the reload cost. From the code, every action ended in `GET /api/results`, and a bulk action made one POST per group (49 POSTs, then a full reload).

After (release/0.3.0, measured in the browser with `performance.getEntriesByType("resource")`):

| Action | Requests after the click | Time |
|---|---|---|
| Ignore from the grid | `POST /api/ignore`, `GET /api/trash` (count), no `GET /api/results` | n/a |
| Keep best in the viewer (one group) | `POST /api/trash` 78 ms, background `GET /api/trash`, no `GET /api/results`; viewer moved to the next group | 78 ms |
| Extract 2 of 3 in the viewer | `POST /api/results/extract` 326 ms, no `GET /api/results` | 326 ms |
| Ignore in the viewer | `POST /api/ignore`, no `GET /api/results` | n/a |
| Keep best, trash rest, 49 groups | one `POST /api/trash` 1417 ms, no `GET /api/results`; one undo record | 1417 ms |
| Undo (negative control) | `POST /api/undo` then `GET /api/results` (a full reload is expected here) | 1351 ms |

Extract survives a scan: after a changed-settings scan and after an unchanged (reused) scan the extracted group is still there once, with the same id.

Not measured: stacking in Immich (needs a real Immich and a group Kevin picks).
